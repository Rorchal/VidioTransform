# ctxgc — 依赖图上下文压缩

借垃圾回收的"从根追踪"思路做 LLM 上下文压缩，但做了三处关键改动：
**可达 / 不可达 → 距离分级（L0 原文 / L1 摘要 / L2 一句话 / L3 存根）**，
**删除 → 换出 + 存根（永不删除，可取回）**，
**加一层"状态 vs 历史"（被取代 / 被否决的内容变墓碑）**。
设计推导见 [docs/design-notes.md](docs/design-notes.md)。

## 目录

```
src/ctxgc/
  model.py       节点 / 边 / 图；边 src→dst = "src 重要则 dst 也重要 × 强度"
  ingest.py      transcript → 节点 + 结构边（调用↔结果、读取、链、请求→回复）；用户消息拆到句子级事实
  edges.py       免模型的边：共享标识符、赋值取代、提案否决、问题→轮次的词面重叠（聊天用）
  propagate.py   从根传播强度（路径连乘、多路径取最大）；帧弹出；近因下限
  summarize.py   每个节点的 4 档版本（抽取式；可换成 LLM）
  allocate.py    按预算分配档位：密度贪心 + 级联拉前提 + 可达优先 + 墓碑固定
  render.py      输出；连续存根折叠成一行
  compress.py    流水线入口 + 基线（full / truncate / random / uniform / gc_binary）
  llm.py         模型做的两步：建边（每个文本块一次调用）和 L1/L2 摘要；DeepSeek / Anthropic 后端，回复缓存成 JSONL
evalkit/
  synth.py       合成 agent 对话 + 真值（角色、边、取代、否决、问答）
  metrics.py     答案保留、可取回、旧值曝光、边的 P/R
  run.py         跑评测，输出 evalkit/results/summary.md；--llm 加上模型建边 / 模型摘要四种方法
  real.py        真实 agent 轨迹上的免标注评测：SWE-agent 轨迹 / Claude Code 会话日志 → 切点 → "后面用到的标识符还在不在"
  chat.py        非 agent 会话评测：LongMemEval / LoCoMo 的长聊天历史 + 末尾问题 → 答案和标注的证据轮次还在不在
  qa.py          官方口径：模型在压缩后的历史上答题，再由模型判分；--dry-run 不调用模型，先算出 token 量和价格
tests/           35 个单元/端到端测试（模型相关的用假模型跑，不联网）
```

## 运行

```bash
pip install pytest
python -m pytest -q                              # 19 passed
python -m evalkit.run --cases 30                 # ~10s，结果在 evalkit/results/
python -m evalkit.run --cases 30 --llm deepseek  # 加上模型建边 / 模型摘要；需要 DEEPSEEK_API_KEY

# 真实轨迹：Nebius 公开的 SWE-agent 轨迹（任取一个 parquet 分片，约 90MB）+ 自己的 Claude Code 会话日志
pip install pyarrow
curl -L -o shard.parquet https://huggingface.co/datasets/nebius/SWE-agent-trajectories/resolve/main/data/train-00006-of-00012.parquet
python -m evalkit.real --swe-agent shard.parquet --n 60 --skip 10 --claude-code ~/.claude/projects/<proj>/<session>.jsonl

# 非 agent 会话：LongMemEval（278MB）和 LoCoMo（3MB）
curl -L -o longmemeval_s.json https://huggingface.co/datasets/xiaowu0162/longmemeval/resolve/main/longmemeval_s
curl -L -o locomo10.json https://raw.githubusercontent.com/snap-research/locomo/main/data/locomo10.json
python -m evalkit.chat --longmemeval longmemeval_s.json --n 60 --locomo locomo10.json --per-conv 5

# 模型答题 + 模型判分（花钱；先 --dry-run 看价格，再去掉 --dry-run 加 --llm deepseek 跑）
python -m evalkit.qa --longmemeval longmemeval_s.json --n 120 --budgets 0.2 0.35 --dry-run
python -m evalkit.qa --longmemeval longmemeval_s.json --n 120 --budgets 0.2 0.35 --llm deepseek
```

模型回复缓存在 `evalkit/results/llm_cache.jsonl`（已提交），所以第二条命令在没有凭证的机器上也能原样复现下面的数字（全部命中缓存，0 次调用，约 20s）。改了提示词才会重新调用。

## 结果二：真实 agent 轨迹（免标注）

合成集只有一个骨架，说明不了真实表现，所以加了一套不需要标注的评测（`evalkit/real.py`）：把一条真实轨迹在中途切开，压缩前半段，看 **agent 后半段自己用到的标识符**（文件名、函数名、常量、带单位的数、报错码）里，有多少在前半段被工具输出发现过、而且还在压缩后的上下文里。agent 的"未来"就是它工作集的真值。另外三个量：**可取回**（在，或者持有它的节点的存根还在）、**不重读**（后面命令里点名的文件路径还在原文里，丢了就得重新 open）、**目标保留**（开头请求里的标识符，agent 后面还在用的）。

数据：Nebius 公开的 SWE-agent 轨迹（Llama 70B 跑 SWE-bench 类任务，一个 issue、十几步工具调用、前缀约 8k token）。分配器的改动在 10 条上选、在 60 条上验，下表是**第三份没碰过的 60 条（65 个切点）**。模型摘要只对 80 token 以上的工具结果调用（Flash 关思考，317 次调用，42 万输入 token，¥0.36）。

| SWE-agent 60 条 | 用到的标识符还在 @10% | @20% | @35% | @60% | 不重读 @10% | @20% | 目标保留 @10% | @20% | 可取回 @10% |
|---|---|---|---|---|---|---|---|---|---|
| truncate | **0.67** | **0.84** | 0.89 | **0.98** | 0.66 | 0.80 | 0.60 | 0.67 | 0.67 |
| random | 0.52 | 0.73 | 0.85 | 0.95 | 0.82 | 0.94 | 0.69 | 0.78 | 0.52 |
| graded（默认） | 0.53 | 0.66 | 0.81 | 0.91 | 0.86 | 0.95 | 0.59 | 0.84 | 1.00 |
| graded-agent | 0.60 | 0.70 | 0.82 | 0.92 | 0.91 | 0.97 | 0.78 | 0.90 | 1.00 |
| graded + 模型摘要 | 0.57 | 0.73 | **0.90** | 0.96 | 0.87 | **0.99** | 0.65 | 0.84 | 1.00 |
| **graded-agent + 模型摘要** | **0.67** | 0.81 | **0.90** | 0.96 | **0.92** | 0.97 | **0.82** | **0.92** | 1.00 |
| graded，开头整段钉原文（旧规则） | 0.09 | 0.22 | 0.53 | 0.84 | 0.05 | 0.34 | 1.00 | 1.00 | 1.00 |

本仓库这次开发的 Claude Code 会话（约 8 万 token 前缀、十几轮用户发言，只有 1 条、2 个切点）：截断 0.43 / 0.54 / 0.66 / 0.79，graded-agent + 模型摘要 0.37 / 0.52 / 0.68 / 0.83。这条日志每次重跑都在变长，切点跟着挪，两种方法互有胜负，一条轨迹不作结论。

`graded-agent` = 分配器的升档增益改成"这一档比上一档多出几个标识符"（`gain="idents"`），其余同默认。默认和 agent 配置都包含两条真实数据逼出来的规则：开头请求保底到"占预算 30% 以内的最细档"，而且要等其他可达节点分完才能再升档。

## 结果三：非 agent 会话（LongMemEval、LoCoMo）

聊天历史加末尾一个问题，没有工具调用。LongMemEval_s：用户和助手的长对话，每题 50 个会话约 12 万 token，带答案和证据轮次标注，六类问题；为了让分配器跑得动，每题只保留证据会话加随机干扰会话到 120 轮（约 3.2 万 token、228 个节点），六类各取 10 题。LoCoMo：10 段双人长对话，说话人 A 当用户、B 当助手，每段取 5 题（去掉无答案的对抗类）。聊天里没有代码标识符，符号边连不上，所以加了一个免模型的**词面重叠边**：末尾问题指向和它共享稀有词的轮次（`graded+lex`）。

## 结果四：模型答题（官方口径，DeepSeek V4.1-Flash 作答与判分）

结果三量的是"证据还在不在"，这里按两个数据集自己的协议来：模型只看压缩后的历史回答问题，再由模型对照标准答案判对错。作答和判分都用 Flash、关思考；三组一共 2289 次调用、2200 万输入 token，**¥17.2**（半价时段）。判分比论文用的 GPT-4o 宽松，所以绝对分数不能和排行榜比，方法之间的差距可以比。

| 答对率 | 题数 | 全量上下文（上限） | truncate @20% | @35% | graded @20% | @35% | graded-agent + 词面边 @20% | @35% |
|---|---|---|---|---|---|---|---|---|
| LongMemEval 裁剪版（3.1 万 token） | 120 | 0.62 | 0.23 | 0.32 | **0.51** | 0.56 | 0.49 | **0.63** |
| LongMemEval 全长版（12.6 万 token） | 30 | 0.47 | 0.23 | 0.40 | **0.47** | **0.53** | 0.33 | 0.47 |
| LoCoMo（2.4 万 token） | 50 | 0.76 | 0.14 | 0.24 | 0.10 | 0.14 | **0.20** | **0.34** |
| LongMemEval 全长版，换 **Claude Haiku 4.5** 作答与判分 | 90 | 0.59 | 0.19 | 0.28 | **0.50** | 0.57 | 0.49 | **0.63** |

最后一行用的是 `claude` 命令的无头模式（`--llm claude-cli:claude-haiku-4-5-20251001`），走 Claude 订阅额度而不是 API 余额：90 题 1090 次调用、3330 万输入 token，CLI 折合的 API 价约 $81。两个作答模型在全长版上的结论一致：压缩到 35% 比不压缩答得好（0.63 对 0.59），截断在每个预算都最差。

LongMemEval 裁剪版按类型 @20%：graded 在 用户单会话 0.95 / 时间推理 0.40 / 多会话 0.45 / 知识更新 0.65 / 助手单会话 0.45 / 偏好 0.15；截断对应 0.20 / 0.15 / 0.05 / 0.65 / 0.30 / 0.05。完整表格在 `evalkit/results/qa_*.md`。

## 主要发现

1. **20% 预算以上，分级 + 换出明显优于截断、均匀降档和二值 GC**；35% 时 0.98 对 0.86。二值 GC 和截断表现一样——可达性本身不是瓶颈，分辨率分级才是。
2. **墓碑是最干净的收益。** 旧值被当作有效内容呈现：graded 0%，其他方法 77–100%，全量上下文本身也是 100%（它把判断"哪个值是现在的"推给模型）。
3. **存根的固定开销比想象的大，而且随节点数线性涨。** 真实前缀 60 多个节点，带 3 词预览的存根组要 512 token，占 10% 预算的 78%；改成只留 id 和角色计数后 137 token。到了 LoCoMo（420 轮拆成 1100 多个节点），光 id 列表就占全文 12%，10% 预算根本放不下。现在连续被换出的块写成 id 区间（`#m12 … #m57 — 112 chunks`），id 按消息序号确定，区间照样能点名任何一块，存根开销变成 0.1%。预览还曾在合成集上直接泄露答案（闲聊里的颜色），去掉后 chatter 列才是真实水平。
4. **开头请求不能整段钉死。** SWE-agent 的开头是 issue 全文加指令模板，约 1100 token，一个节点就超过 10% 预算。现在钉住只保证"占预算 30% 以内的最细档"，之后和别的节点一样竞争升档。这一条在合成集上没有体现，因为合成的目标只有三句话。
5. **免模型建边的缺口**：精确率 0.10（过度连边，128 条 vs 真边 24 条）、召回 0.53；旧值墓碑 100%（但归因到确切的更新句只有 37%，常是助手的确认句触发的）；否决检出 63%；用户句子角色准确率 57%，**完全分不出闲聊和指令**。
6. **模型建边把这个缺口补上了大半**：精确率 0.41 / 召回 0.77，墓碑归因 100% / 100%，闲聊 100% 识别。剩下的误报多是"每句助手叙述都 supports 目标"（真边表里没有这类边，但传播上无害）；剩下的漏报主要是"fix 决策 → 目标"这条边被每块 4 条的上限挤掉（30 例漏 24 次）。角色错误里 30/30 是把收尾的 "Great." 标成 user——真值把它标成 goal，模型其实更对。
7. **合成集上边不是瓶颈，摘要是。** 模型建边单独上场，答案保留和启发式一样（0.78 对 0.81 @20%）。换成模型摘要，20% 时 0.81→0.85，35% 起全部 1.00；深层事实 @20% 从 0.03 到 0.28。模型摘要的好处是任务相关：给它开头那轮用户消息当上下文，它从 140 行日志里挑出带 TODO 注释、延迟数字的那几行。
8. **真实 SWE-agent 轨迹上，截断是很强的基线。** agent 下一步用到的东西 48% 就在上一步的工具输出里，只有 16% 在 4 步以前；而且 agent 要的是原文（函数名、行号），不是摘要。截断把全部预算花在最近的原文上，正中要害。第一版 graded 在 20% 预算只有 0.45：预算的 33% 花在开头请求上（issue 全文加指令模板，作为根分数 1.0，保底之后一路升档），工具结果原文只占 8%，截断是 65%。
9. **三步追上来，每步都是看了预算去向才改的。** (a) 开头请求等其他可达节点分完再升档：0.45→0.64（默认）、0.72→0.79（agent 配置），合成集一个数没动。(b) 增益改成标识符数（agent 配置）。(c) 模型摘要：60% 预算时丢的标识符全在停在 L1 的工具结果里，66/68 的抽取式摘要没包含它——抽取式摘要猜不到 agent 下一步要改哪个函数，给了开头请求当上下文的模型摘要能猜到一部分。三步叠加，新样本上 0.69 / 0.80 / 0.89 / 0.96 对截断 0.67 / 0.84 / 0.89 / 0.98，另外三项全面领先：可取回 1.00 对 0.67，不重读 0.92 对 0.66，目标保留 0.81 对 0.60（@10%）。**random 也不弱**（60% 时 0.95）：标识符通常出现在多个节点里，随机留整块原文就能覆盖——"整块原文 vs 什么都不留"好过"每块一个抽取式摘要"。
10. **增益函数要和消费者匹配，而且 10 条轨迹不够选参。** 标识符增益在合成集上丢闲聊和纯文字决策（0.81→0.70 @20%），在真实轨迹上有收益；它在 10 条选参轨迹上 @10% 是 0.65，第一份留出样本 0.53，第二份 0.58。所以它是显式配置，不是默认。
11. **聊天历史和 agent 轨迹正相反：这里截断最差，图方法大胜。** LongMemEval 20% 预算下证据轮次保住 0.85 对截断 0.30，35% 时 0.92–0.98 对 0.45。原因也查清楚了：证据 282 条在用户轮次、9 条在助手轮次，而用户轮次占节点 74%、只占 token 13%。本方法把每句用户话当根，20% 时 92% 的用户句子留在原文或摘要档，正好对上"记忆在用户说的话里"；截断按时间丢，随机按块丢，都不区分谁说的。这是设计里"用户事实拆到句子级、全部当根"那条规则的收益，第一次在真实数据上看到。
12. **弱点在答案藏在助手长回复里的时候**（LongMemEval 的 single-session-assistant：20% 预算下证据只保住 0.20）。助手回复长、没有根身份、只靠用户问句的 SERVES 边拿到 0.4 的强度，就被降到一行或一段摘要，长回复的摘要留不全。词面重叠边从末尾问题连过去，把证据轮次的原文率从 0.54 提到 0.60，agent 配置再到 0.72，但对这一类还不够：需要检索式的边加上足够的预算把整段回复升回原文，符号标识符边在聊天里几乎是空的。
13. **LoCoMo 上图方法也赢，但差距小、而且是区间存根救回来的。** 1100 多个节点让存根 id 列表吃掉全文 12%，20% 预算下默认方法证据只剩 0.05，比截断还差；区间存根把开销压到 0.1%，默认 0.24、agent 配置 0.39，对截断和随机的 0.16。60% 预算时随机 0.57 仍高于默认 0.51——短轮次的一行摘要在默认分配器眼里等于全文，它不再给原文（原文率 0.03），agent 配置给（0.20 → 0.40）。两个聊天数据集加起来的结论：聊天历史里图方法稳定好于截断，优势来自"用户句子都是根"和"任何块都能要回来"；短板是长的助手回复和"摘要等于全文"时的原文率。
14. **证据保留率的优势在模型答题上保住了，而且全长历史上压缩比不压缩还好，换作答模型也成立。** LongMemEval 裁剪版 20% 预算：graded 0.51 对截断 0.23，差 28 个点，上限 0.62。全长 12.6 万 token 的版本，Flash 30 题：全量 0.47，graded 20% 0.47、35% 0.53；Haiku 4.5 90 题：全量 0.59，graded 20% 0.50、35% 0.57，agent 配置 35% 0.63。两个模型都是压到 35% 比读全文答得好，截断在每个预算都最差。这是设计笔记里"活的内容也要压，太长模型也会变差"那句话第一次有数字。agent 配置在 Flash 的 30 题上偏差（0.33 / 0.47），在 Haiku 的 90 题上最好（0.63），小样本上它的方差大。
15. **LoCoMo 上默认配置输给了截断（0.10 / 0.14 对 0.14 / 0.24），agent 配置最好（0.20 / 0.34），都远低于 0.76 的上限。** 看了压缩后的文本：默认分配器把预算摊在全部 19 个会话上，193 行用户句子的摘要、120 行助手回复被截到 16 个 token 的一行版，要找的那一轮没进去；截断留的是最近三分之一的原文，证据恰好常在里面；agent 配置偏深度优先，178 行原文。双人对话里一半证据在被当成"助手"的那一方，图对它没有根信号，词面边只补了一点。这里需要的是检索质量的边。n=50 时 0.10 和 0.14 只差两道题。
16. 几个会让数字偏乐观或偏悲观的地方：(a) 合成集的深层事实依赖抽取式摘要器按"对话里提过的标识符"挑行，所有方法共用；(b) 合成集指标是字符串匹配，"TODO to batch the queries" 对不上 "TODO batch this"，模型摘要被低估；(c) 真实轨迹指标数的是标识符，graded-agent 的增益也数标识符，两者耦合——"不重读"、"目标保留"不受这个影响，"用到的标识符还在"受；模型摘要那一列不含标识符增益以外的耦合。

## 限制

- 模型只跑了 DeepSeek V4.1-Flash（30 例：建边 615 次调用 / 61 万输入 token，摘要 1167 次 / 50 万；16 线程 8 分钟）。V4 Pro 建边跑了 10 例就停了（精确率 0.46 / 召回 0.68 / 角色 0.89，比 Flash 边更少更准），没跑完不进表。Anthropic 后端写好了没跑。建边提示词不是在真值上调出来的，只按设计笔记里的边语义写。
- 真实轨迹上的模型摘要只给了 80 token 以上的工具结果，上下文只有开头那轮用户消息。给它更多上下文（最近几步助手在干什么）大概率还能涨。
- 模型答题（结果四）用 Flash 判分，比 LongMemEval 官方的 GPT-4o 判分宽松，绝对分数不能和排行榜比；题量 120 / 50 / 30，方法间差距小于 10 到 15 个点时不可靠。结果三的 LongMemEval 裁到了 120 轮，结果四的全长版只有 30 题。LoCoMo 把说话人 A 当用户、B 当助手是任意的映射。
- 真实轨迹评测衡量的是"后面用到的东西还在不在"，没有把 agent 真的接上压缩后的上下文续跑。续跑才能测重复劳动、约束违反和任务成败，Nebius 数据带每条轨迹的通过/失败标签，可以做。
- token 数是 chars/4 的近似，只用于方法间同预算比较。
- 单次快照，没测多轮之间的稳定性（滞后阈值未实现）。
- 本轮修了一个存根 bug：节点很短时 L3 存根比 L2 还长，旧代码会把存根换成 L2 文本，存根就丢了 id、也不能折叠。修完 uniform 基线在 10%–20% 掉了几个点（它之前靠"存根其实是整句"占了便宜），其他方法没动。
